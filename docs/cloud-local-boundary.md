# 云端与本地的职责边界

本文基于当前源码给出判断，并指出现有实现与"案件内容留本地"这一表述之间的**实际落差**。
结论先行，理由在后。

---

## 0. 核心结论

**当前架构已经做对了存储边界，但没做推理边界。**

- 案件本体（原件、OCR 文本、案件记忆、文书、联动结果、代理立场、草稿）确实全部落在本地
  `workspace.sqlite` 与 `storage/`，云端一行案件内容都没有。**这一点是对的，不要改。**
- 但发布态的 `AI_GATEWAY_MODE=cloud`（`app/.desktop/server/.env.local` 硬编码）意味着：
  材料理解、文书生成、句级联动、案件助手这四类任务的**完整提示词都会经过云端网关，
  再转发给模型供应商**。案件内容事实上离开了本机，只是没有落在云端磁盘上。

这两件事不矛盾，但表述上容易误导。README 已用"本地保存不等于全部处理离线"做了免责，
本文要把边界划到更细的粒度。

---

## 1. 判断依据

排优先级从高到低：

| 判据 | 含义 |
| --- | --- |
| **律师保密义务** | 案卷材料受《律师法》第三十八条保密义务约束；当事人身份信息、标的金额属个人信息。泄露的法律后果由律所承担，不是产品事故 |
| **最小必要原则** | 只有跨设备、跨用户、跨组织协作必需的数据才需要离开单机 |
| **成本归属** | 模型调用成本随 token 走，谁付钱谁的服务在谁的机器上跑更清晰 |
| **延迟与带宽** | 原件动辄数百 MB、上千页，走网络在物理上不划算 |
| **离线可用** | 法庭、法院、律所现场网络常常不可靠，核心办案能力不能因为断网失效 |

## 2. 当前实现的真实边界

以下都是**代码事实**，不是设计意图。

| 数据 | 现在的实际流向 | 落点 |
| --- | --- | --- |
| 原件字节 | 桌面端本地 | `userData/storage/evidence/...` |
| OCR / PDF / Word 解析 | 桌面端 fork 出 document-worker 子进程 | 本地内存与本地文件 |
| 案件记忆、文书、联动、立场、草稿 | 桌面端本地 | `userData/data/workspace.sqlite` |
| **材料理解提示词** | 桌面端 → **云网关** → 模型供应商 | 网关不落盘，但内容过网 |
| **文书生成 / 联动提示词** | 同上 | 同上 |
| **Embedding 输入文本** | 桌面端 → **云网关** → 供应商 | 同上 |
| MCP 案例检索关键词 | 桌面端 → 云网关 → 元典/威科/法宝 | 云网关记 actor，不记 query |
| 官方法源核验 | 桌面端**直连** `flk.npc.gov.cn` | 不经云 |
| 账号 / 积分 / 订单 / 发票 | 云端 | PostgreSQL |
| 模型密钥 | 云端持有 | cloud-server 环境变量 |
| 遥测 | 云端 | 仅事件名 + 耗时 + 成败，**无内容** |
| 知识库向量（commercial 模式） | chunk 文本过网关取向量，向量存 Qdrant | Qdrant（云端） |

### 已经做对的地方

这几处值得保留，不要在后续重构中破坏：

1. **网关不落案件内容**。`ai_request_store` 只存 `actor`（userId/organizationId/role）和状态；
   `chat-provider.ts` 与 `ai.ts` 的失败日志只记 hostname 与状态码，不记请求体。
2. **遥测无内容**。`analytics-service.ts` 的事件 schema 是封闭枚举
   （`app.open` / `document.import` / `evidence.link` 等）+ `durationMs` + `outcome`，
   且必须用户在账户中心显式开启 `analytics-preference` 才上报。
3. **官方法源走直连**。`searchNpcStatute` / `fetchNpcDetail` 在桌面端直接请求全国人大法规库，
   只送法条名称，不送文书上下文。这是最该保持的隐私姿态。
4. **模型调用缓存留本地**。`llm-cache/<account>.json` 在本地，
   缓存命中即省一次出网调用。
5. **计费与推理分离**。`direct` 模式下推理本地直连，但计费仍走云端
   （`case-agent-billing.ts` 的 `startCharge` 调 `/api/account/points/consume`）。
   推理可以本地，账本必须唯一，这是对的。

## 3. 建议的分层

不是"上云 / 不上云"的二元选择，而是按敏感度分三档。

```text
第一档：账号级 —— 全部上云
  账号身份、组织成员、积分账本、订单、发票、模型密钥、发行与更新
  理由：与案件内容无关；跨设备必需；成本与合规责任清晰

第二档：知识级 —— 默认本地，可选上云
  法律条文库、判例库、内置法库、律所自建知识库
  理由：公共法规本来就公开；律所自建库是"团队资产"，
        多人共享时上云合理，单人使用时留在本地更省事
  关键：同一份文件的 chunk 文本不能既用于本地检索又过云做向量

第三档：案件级 —— 绝不落云，只在推理时过网
  原件、OCR 文本、案件记忆、文书、联动结果、代理立场、草稿
  理由：保密义务；本机性能已足够；离线必须可用
  注：第三档那句"只在推理时过网"是当前最需要用户知情的一层。
      它不是缺陷（模型必须看到内容才能理解），但必须是明示选择，
      而不是安装包里的硬编码默认值。
```

---

## 4. 逐项建议

### 4.1 保持本地，不要动

| 项 | 理由 |
| --- | --- |
| 案件工作区 `workspace.sqlite` | 保密义务 + 离线可用 + 现有 sqlite 快照合并机制已够用 |
| 原件 `storage/` | 体积与带宽；同时它是"人工核对"环节的唯一依据 |
| 解析 worker（mammoth / pdf-parse / 旧版 .doc） | 纯 CPU，零边际成本，出网毫无收益 |
| 规则化风险扫描 `evidence-risk-scan.ts` | 正则匹配，无模型、无成本；且它是超大材料唯一全覆盖的检查 |
| 句级门控 `linkage-policy.ts` | 纯规则守卫，排除标题/身份字段/套话，不需要模型 |
| 官方法源直连 | 只送法条名称，最小暴露 |
| 本地 RAG 索引 `knowledge-rag-index.json` | 内置法库的向量在本地，检索不出网 |
| 本地模型调用缓存 | 缓存命中省一次出网调用 |

### 4.2 应该上云

| 项 | 理由 |
| --- | --- |
| 账号、组织、RBAC | 已实现。组织级权限（`rbac.ts`）在云端才有效，桌面端做不了多用户授权 |
| 积分账本 + 幂等扣退费 | 账本必须唯一。多端并发扣费只有中心化才能保证幂等键生效 |
| 模型网关与密钥托管 | 密钥下发桌面端等于放弃计费控制与轮换能力；网关同时是限流与审计点 |
| 发行、更新分发、校验和 | 已经是纯云端形态，正确 |
| 匿名化产品度量 | 已实现且已做内容剥离，正确 |
| 公共法规 / 判例的**规范化结构** | 全国人大库、司法部库、政府规章库的同步是重活，集中做一次全网可用，本地重复拉取是浪费 |
| 律所级知识库（多人协作场景） | 团队资产天然需要共享，但要走第二档的显式开关 |

### 4.3 需要产品决策的灰区

**① Embedding 到底在哪算**

现在 `embedding-service.ts` 的 chunk 文本会经云网关取向量。
如果知识库是律所私有文档（合同模板、内部指引），chunk 文本就是私有内容。

建议：把"向量计算位置"与"向量存储位置"拆开。
向量计算走直连（客户端持有 embedding key 或网关提供本地化端点），
向量存储按第二档决定留本地还是上云。
当前代码里 `KNOWLEDGE_RAG_MODE=local|commercial` 这个开关只管了后者。

**② MCP 案例检索的 query**

现在关键词过云网关转发。检索词本身通常不含案件机密
（"买卖合同 违约金 最高院"），可接受。但要防止将来有人把整段文书塞进 query。
建议在网关侧对 `tools/call` 的参数做长度与结构校验——现在只校验了工具名白名单。

**③ 遥测开关的默认值**

现在默认关闭、需显式开启。对律所客户这是对的。
但同一份代码里 `app.open` 也会上报，建议保持现状不动。

## 5. 三个必须处理的落差

### 落差一：发布态推理模式被硬编码为 cloud

`app/electron/prepare-desktop.cjs` 写死：

```text
AI_GATEWAY_MODE=cloud
CLOUD_API_BASE_URL=https://lawagent.zhijing.fun
```

用户无法在安装包里选择"本地直连模型"。这有两个后果：

1. **保密承诺不完整**。装上就能用是好事，但用户应当知道并能选择
   "这份案卷会不会经过贵司服务器"。目前的答案是会，且无从选择。
2. **商业模式与隐私诉求绑死**。有些律所有本地部署模型的要求
   （涉密案件、内网隔离），当前产品形态直接不支持。

**建议**：保留 cloud 作为默认（否则用户要自己配 key，转化率崩塌），
但在设置里给出显式选项：

| 选项 | 行为 |
| --- | --- |
| 经平台网关（默认） | 现状。计费走云端，内容过网，可获得云端模型目录与统一限流 |
| 本地直连自备模型 | 用户填自己的 baseUrl / apiKey / model，**内容不经过贵司服务器**，计费仍走云端积分 |
| 完全离线 | 不计费、不可用智能功能，其余本地能力全部可用 |

第二种模式代码上已经存在（`AI_GATEWAY_MODE=direct` + `LLM_BASE_URL`/`LLM_API_KEY`），
缺的只是桌面端的配置入口与凭据保管方式。

### 落差二："本地保存"这句话容易被读成"内容不出本机"

README 与官网措辞是"案件与原件在本地保存"，同时又有一句免责。
但两句话之间隔得太远，普通用户不会读到第二句。

**建议**：在首次启动与设置页用一句话说清事实——

> 案件文件保存在本机；使用智能分析时，相关内容会发送至 {模型供应商 / 平台网关}。

这不是营销措辞问题，是律师向当事人履行告知义务的前提。
产品定位与法律定位在这里是同一件事。

### 落差三：多端协同与"案件不上云"互斥

当前每账号一个本地工作区（`data/workspaces/<slug>/`），云端不存案件。
这意味着**同一案件无法在两台电脑上协作**。

这是取舍，不是疏漏。要协同就得动边界，两个方向：

| 方案 | 做法 | 代价 |
| --- | --- | --- |
| A. 维持不上云 | 放弃多端协同 | 律师换电脑要手动迁移；团队协作靠拷贝文件 |
| B. 端到端加密同步 | 本地加密后上云，云端只存密文 | 密钥管理（口令 / 设备密钥）成为新的安全面；协同时密钥分发是难点 |
| C. 案件上云 | 案件内容进 PG + 对象存储 | 保密承诺实质改变，需重新做合规与产品定位 |

**我的判断**：现阶段选 A。律师的主要协作对象是文书和结论，不是共同编辑同一个案卷。
真出现协作刚需，再上 B——B 保留了"平台永远看不到内容"这个核心承诺，
而 C 会一次性推翻它。

---

## 6. 若要改动，按这个顺序

1. **加设置项**：`AI_GATEWAY_MODE` 三选一 + 本地模型凭据的存储位置（系统钥匙串 / 加密文件 / 明文）。
   这是唯一能让"保密承诺"变成"用户可选行为"的动作。
2. **加明示文案**：首次启动与设置页说明内容流向。
3. **拆 embedding 的计算位置与存储位置**，让第二档知识库能真正做到"向量不出网"。
4. **网关补 `tools/call` 参数校验**，防止 MCP query 被塞进案件正文。
5. 前面四项做完之前，**不要**碰第三档的任何东西——案件工作区、原件、解析、规则扫描，
   现状是对的。

---

## 7. 一句话总结

> 账号上云、案件留本地、知识库看协作需求——
> 但要把"推理默认过网关"这件事从安装包的硬编码，变成用户能看见、能选择的开关。
