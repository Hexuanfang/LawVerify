## 0. 两个问题的结论

### 问题一：不同文书类型，是否需要建立对应的元素拆解清单？

**需要。**

PRD §3.3 给了 12 类声明和 10 类文书，但那是全集。如果用一份全局 `ELEMENTS` 跑所有文书，证据清单会去查法条、上诉状会漏掉空泛指错、起诉状会拆出不该有的质证。

落地方案：**10 份 profile，三档级别（必拆 / 选拆 / 不拆）**。

- 机器可读：`doc-element-profile.json`（同目录，直接 import）
- 人读规格：`01-文书类型元素拆解清单.md`
- 代码改造点：`src/utils/review.js` 的 `ELEMENTS` / `checksFor` 改为按 `docKey` 查 profile

身份元素完整清单以 `doc-element-profile.json` 的 `identityElements` 为准（抽不到等于没做这类文书）：

| 文书 | identityElements |
| --- | --- |
| 起诉状 | E-SUBJ、E-CLAIM、E-FACT、E-CALC、E-LAW、E-PROC |
| 答辩状 | E-SUBJ、E-CLAIM、E-FACT、E-LAW、E-CROSS |
| 证据清单 | E-EVID、E-PURP |
| 质证意见 | E-EVID、E-CROSS |
| 代理词 | E-CLAIM、E-FACT、E-LAW、E-FOCUS |
| 上诉状 | E-SUBJ、E-CLAIM、E-LAW、E-PROC、E-ERR |
| 再审申请书 | E-SUBJ、E-CLAIM、E-LAW、E-PROC、E-FOCUS、E-ERR |
| 律师函 | E-SUBJ、E-CLAIM、E-FACT、E-LAW |
| 法律意见书 | E-SUBJ、E-FACT、E-LAW、E-FOCUS |
| 程序类 | E-SUBJ、E-CLAIM、E-LAW、E-PROC |

### 问题二：核验的 benchmark 怎么制定？

**用数字判定，不用"效果不错"。** 完整规格在 `02-核验Benchmark与达标判定.md`，要点：

1. **十条红线一票否决**（编造案号法条、缺源装联动、引文不一致、判项反转、闸门失效……）。任一命中 = 不达标。
2. **金标集**：种子用现有 c1/c2 演示案（必须全过），扩充到 ≥30 份文书 ≥200 条声明 + 12 条对抗样本。
3. **硬指标**：必拆召回 ≥95%、红灯检出 ≥95%、缺源不编造 =100%、导出闸门 =100%。
4. **分档**：不达标 / 基本达标（内测）/ 达标（可交付）/ 优秀。
5. **借鉴 AutoClaw**：`legal-qa` 当导出门禁原型；`legal-norm-validity-check` 的效力 7 态与置信度；`legal-article-retrieval` 的 Recall/Precision 当检索层基线。

## 2. 推荐实施顺序

```
P0  让现有演示不自相矛盾
    ├─ 加载 doc-element-profile.json
    ├─ checksFor(item, docKey) 替换全局 ELEMENTS
    └─ off 类型误报标记
P0  红线进代码
    ├─ R1–R10 写进判定器
    ├─ 导出闸门 = fail|miss|pending
    └─ AI/MCP 产出一律 pending
P1  金标集
    ├─ 从 cases.js 导出 expected JSON（种子）
    ├─ 补 ADV-01~12 对抗样本
    └─ npm run bench 出 benchmark-report.json
P1  判定器
    ├─ A1–A5 / B1–B6 / C1–C7 按 02 号 §5 实现
    ├─ E-CALC 必给算式
    └─ 级联降级（事实未核实 → 类案降近似）
P2  扩充集 + 真实 MCP 契约对齐
P2  legal-qa 式导出前自检（本期可半自动）
```

**验收顺序**：种子集回归 → 对抗 12 条 → 指标分档。种子集不过，后面不用看。

## 3. 铁律（写进代码注释也行）

1. 缺源不编造。L1/L2/L3 查无就标缺源，不用相似出处补位。
2. AI 不替代律师。所有 AI 产出一律待核验。
3. 可回查。引号内逐字一致；判项不反转。
4. 达标看 benchmark，不看演示动画好不好看。
