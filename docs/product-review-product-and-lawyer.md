# 产品评审：产品视角 + 律师视角（2026-11-10）

评审对象：LawVerify 桌面端 0.1.60（`app/package.json`）、server / cloud-server / web 现状。
方法：通读 README、docs（pending-decisions / evidence-matching-architecture / feature-gap-implementation）、源码目录与关键实现，并按「产品价值—可交付—执业风险」三条轴做批判性评估。所有"确定点"均可回溯到代码或文档。

---

## 0. 一句话结论

产品在"**生成之后**"这一段（核验层）找到了真实空白，句级锚定 + 侧边对照 + 人工纠偏的闭环设计是同类产品里少见的正确取舍；但**衡量这项能力是否成立的指标（逐句锚定准确率 / 核验覆盖率）至今没有评测集、没有基线、没有对外口径**，而交付侧（导出格式、AI 留痕、数据保密、团队协作）还停在"内部工具"水平。这决定了它现在能演示、能试用，还不能被律所正式采购。

---

## 1. 优点

### 1.1 产品视角

1. **切的是真空白**。市面法律 AI 集中在"生成"，本产品押注"生成结果的可验证性"（原产品方案 P 定位）。这是律师采纳 AI 的最后一公里，付费意愿与差异化都最强。
2. **锚定粒度选对了**。落到句子而非段落/全文摘要，`linkage-policy.ts` 的句级门控、候选 ID 校验、摘录来源检查、引用数量上限，都是围绕"少而准"设计，符合质证场景（逐句核对证据）的实际动作。
3. **核验语义比"看起来很准"更专业**。法条版本分级、废止标红、案号只有官方正文含该案号才显示"已核实"、查询失败只标"未能核实"而不判虚假（`docs/feature-gap-implementation.md`）。这类"负向严谨"是法律 AI 里稀缺的东西。
4. **人机分工写进了产品模型**。主张与证据关系分 `support / partial / contradict / insufficient`；材料区分原始证据 / 文书底稿 / 身份资格材料；明确"代理立场决定论证方向，不改变客观事实"，保留不利材料与矛盾。这套语义经得住执业审视。
5. **成本/体验两头兼顾的意识**。材料理解按内容指纹复用（`server/src/service.ts` 重复文件不重复调模型）、检索式理解按相关度收敛块数、联动结果增量下发而非全量灌流，避免了大材料撑爆响应。
6. **交付形态对律师友好**。桌面安装包内置服务，终端用户不装 Node/Docker/PG/Qdrant；案件与原件本地 SQLite 存储。选"本地工作区 + 云端账户计费"而不是"纯 SaaS 上传"，方向正确。

### 1.2 律师视角

1. **解决的是真痛点**：AI 写完的质证意见与原始 PDF/微信截图/笔录对不上，人工翻页定位极耗时，产品把"点击左句→右侧定位并高亮"做成了主界面（不是藏在设置里的功能）。
2. **留了人工兜底**：手工绑定、解绑、纠正、备注，AI 挂错时律师有出口，不至于"错锚定比不用更糟"（这是同类产品最常见的死法）。
3. **案件记忆降低了重复交代成本**：争议焦点、时间线、主张与抗辩留存，跨文书、跨讨论复用，符合"一个案子来来往往改十版"的真实节奏。
4. **原件与目录同屏**：证据目录 + 原文预览 + 文书工作区在一屏内，减少窗口切换，这是效率的真实来源。

## 2. 缺点（问题清单，按严重度）

### 2.1 严重（阻断律所采购）

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| S1 | **核心指标不可度量**：全仓 `准确率 / 召回率 / 评测 / 基准` 零命中，无标注集、无离线评测 | 原方案明确写「锚定准确率 >80% 可用，<60% 需重新设计」为上线前置条件，未见落地 | 销售无法证明"比人工快"，无法定价，无法发现模型升级后的静默退化 |
| S2 | **保密边界不满足律所采购门槛**：桌面发行配置固定 `AI_GATEWAY_MODE=cloud`（`app/electron/prepare-desktop.cjs:41`），材料内容经官方云端网关处理；无本地模型档位、无私有化部署、数据不训练/不留存的合同级承诺缺失 | 同上 | 涉密案件与多数规模化律所无法通过内部保密审批，采购直接被挡 |
| S3 | **交付物不合执业格式**：Word 导出只有正文 + 灰色小字"批注："（`app/src/export-word.ts`），无案号/当事人/页码/落款/页眉页脚、无真实 Word 批注与修订、无 PDF 导出、无证据目录页 | `app/src/export-word.ts` | 产物不能直接递交法院或装订成册，律师仍需二次排版 |
| S4 | **无 AI 生成与核验留痕**（P-06 未做）：段落级无 AI 标识、无声明页、核验记录与操作日志不随文书导出；且无操作日志功能（`审计日志 / 操作日志` 全仓 0 命中） | `docs/pending-decisions.md` P-06 | 无法证明"人工核验过程"，与"不替代专业判断"的定位自相矛盾；律所质控、监管检查时是硬伤 |
| S5 | **无团队协作**：除注册填律所名称外，团队/协作相关实现为空（`协作` 0 命中） | 全仓 grep | 律所按席位采购，但产品只支持单兵作业，团队分工、内部复核、成果归属都无处安放 |

### 2.2 中等（影响日常效率与专业深度）

| # | 问题 | 说明 |
|---|---|---|
| M1 | **法律库仅 9 部法律**（民法典、民诉法、刑法、劳动、反不正当竞争、增值税、宪法、网络安全、食品安全），无司法解释、无指导性案例、无行政法规、无地方性法规 | 多数商事争议的请求权基础在司法解释里，检索必然落空；"证据、法条、案例协同核验"目前只能覆盖一半场景 |
| M2 | **无全局检索 / 快捷键**（P-08 已识别未做，全文检索 0 命中） | 一个案子上百份材料时只能目录浏览，核验效率随规模衰减，而这恰是产品宣称的优势场景 |
| M3 | **质证专业结构缺位**：没有证据三性（真实性/合法性/关联性）结构化归类、没有举证责任分配、没有"是否采信"的主张位、没有证据目录自动生成 | 现有能力是"句—证据对齐"，律师真正要写的那套论证骨架仍靠自由文本 |
| M4 | **时间维度缺失**：诉讼时效、举证期限、管辖异议、上诉期、关键行为日期在案件记忆里只是文本字段，无计算、无倒计时、无风险提示 | 律师的高价值产出里"时间风险"是第一位的，产品完全没接 |
| M5 | **编号双轨 + 三轨并存**：目录 E01、文书"证1"、附件 X01（`case-agent.ts:evidenceSourceNumber`），映射关系需人工对照（P-09） | 直接影响法院文书格式合规性——正文引用编号必须与证据目录一致 |
| M6 | **微信截图/扫描件仍是重灾区**：README 自认不承诺完整 OCR 与页内坐标；图片类锚定依赖视觉模型与框选，精度最低 | 微信聊天记录恰是最常见证据；错锚定会把核验成本从"省时间"变成"更费时间" |
| M7 | **"未能核实"是常态体验**：案号核验依赖法院官网公开正文，多数法院无具体页面；官方来源不可达即长期停在"未能核实" | 律师会读成"这功能总是不确定"，需要明确降级解释与旁证路径 |
| M8 | **案件状态不自动流转**（P-01）：材料增删后案件仍停在"已核验" | 归档语义失真，属于合规风险而非体验问题 |
| M9 | **计费点与价值点错配**：扣费在 AI 生成/理解调用，而律师最愿付费的是"核验"（原方案即如此设计）；建立信任阶段就收额度 | 会把最想尝鲜的早期用户挡在门外，也与"上传/核验不扣分"的初衷冲突 |
| M10 | **安装包信任度**：macOS 未完成 Developer ID 签名与公证，Windows 默认不签名（`signExecutable=false`） | 律所 IT 常拦截未签名软件；SmartScreen 提示直接劝退个人用户 |

### 2.3 轻微（工程与体验债）

- `app/src/App.tsx` 11145 行单文件承载主界面；`web/src/site.css` 6131 行硬编码色值，官网与客户端视觉分叉（P-02）。迭代速度与视觉一致性都会被拖住。
- 登录转化漏斗：无"忘记密码"（只能重置）、无"记住我"、注册必填机构 + 负责人 + 邮箱 + 密码（P-05）。
- 增长机制缺位：埋点与邀请奖励默认关闭且尚未上线运营（P-08/feature-gap 中的开关仍为 `false`）。
- 工具栏缺查找替换、字数统计、批注三件高频能力；对齐三态用 `≡ / ≣ / ≡` 字符图标辨识度差（P-11）。
- 最小窗口 1080×720 时三栏布局挤压，正文可用宽度不足 350px（P-12）。
- README 版本号 0.1.52 与 `app/package.json` 0.1.60 不一致，发行信息以文档为准容易出错。

## 3. 确定点（已核实的客观事实，不含推测）

1. 桌面发行配置固定走云端 AI 网关：`AI_GATEWAY_MODE=cloud`（`app/electron/prepare-desktop.cjs:41`），服务端 `env.ts` 默认值是 `direct`，即"本地直连模型"仅存在于自建部署。
2. Word 导出不含声明页、页眉页脚、页码、真实批注；"批注"以灰色 9 磅文字追加在段落后（`app/src/export-word.ts`）。
3. 无任何准确率/召回率评测资产，全仓检索零命中。
4. 内置法律库为 9 个 `.docx`（`files/法律文件/`），用法条级向量索引 + 条文查找。
5. 无团队/协作、无全局搜索、无 PDF 导出、无证据目录生成、无操作日志、无版本对比。
6. 案号核验成功条件为"法院官方具体页面正文包含该案号"，任一环节不可达即"未能核实"（`server/src/intelligence/legal-verification.ts`、`official-case-verification.ts`）。
7. 主张—证据关系分类含 `support / partial / contradict / unrelated / insufficient`；材料角色区分原始证据 / 文书底稿 / 身份资格材料。
8. 段级核验单次上限 30000 字、最多 20 个法条引用 + 10 个案号、总超时 90 秒（feature-gap 文档）。
9. 案卷工作区为本地 SQLite，原件与资产独立存储；桌面数据位于 `%APPDATA%\LawVerify\data|storage`。
10. README 自述版本 0.1.52，实际 `app/package.json` 为 0.1.60。

## 4. 改进点（按建议执行顺序）

### 第一梯队：不做就进不了律所采购流程（约 3 个月）

1. **建评测集，公开口径**。用 50–100 个真实案件的"主张句—证据片段"人工标注，做离线回归：锚定准确率、漏链率、contradict 召回率、错锚定率；每次模型/提示词变更跑一次，把结果挂到版本说明上。这是这个产品唯一能变成资产的东西，也是把"看起来很准"变成"测出来准"的唯一途径。
2. **交付格式合规化**。Word 模板（案号、当事人、页码、落款、页眉）+ PDF 导出 + 证据目录页 + 引用编号对照表；同时把导出批注改成真正的 Word 批注/修订痕迹。
3. **补齐留痕**。文书级 AI 辅助与人工核验声明页 + 每段核验状态（已核验/存疑/未核验）+ 时间戳 + 核验人；引入最小操作日志（谁在何时改了什么、导出过什么）。
4. **保密方案产品化**。提供"完全本地模型"档位（一条配置即可切 `direct` + 本地 endpoint），把遥测做成默认永久关闭且可删除历史，客户端与合同写明材料不留存、不用于训练；同步给出私有化部署路线图（哪怕先以"即将支持"占位）。
5. **统一证据编号**。内部 E 编号与文书"证据 N"保留双轨，但导出《证据目录》对照表，正文引用一律用证据 N；附件 X 编号不进对照表但要在目录里显式说明。

### 第二梯队：决定"用得爽"（3–6 个月）

6. **全局搜索 ⌘K**（P-08）：覆盖材料原文、文书段落、法条、案例，先做材料名 + 段落标题，再扩到原文。
7. **法律库扩容 + 请求权基础链路**：司法解释、指导性案例、行政法规、地方性法规入库，检索按"请求权基础 → 司法解释 → 案例"链路展开。
8. **质证结构化模板**：证据三性归类、证明目的、举证责任分配、"是否采信"主张位，写入正文用模板块，与句级联动打通。
9. **期限与风险清单**：诉讼时效、举证期限、管辖、上诉期自动计算 + 倒计时 + 案件记忆中的风险提示。
10. **团队最小集**：案件共享、只读复核、内部评论与版本对比（先不做客户/法官外部共享）。
11. **签名与公证**：macOS Developer ID + Apple 公证，Windows 签名，解除机构 IT 拦截。
12. **案件状态自动回退 + 核验完成确认提示**（P-01），并补忘记密码、注册减负（P-05）。

### 第三梯队：体验与工程债

13. 官网与客户端设计令牌统一（P-02、P-10）；`App.tsx` 按领域拆分；补查找替换、字数统计、真实批注（P-11）；≤1200px 自动折叠左栏（P-12）；修正 README 版本号。

### 明确不建议现在做的

- **不要先扩生成能力**（多文书类型、自动起草模板库）。当前瓶颈不是"写不出来"，而是"写出来的东西律师敢不敢用"。生成越强，未核验风险越大。
- **不要在评测集上线前扩案例供应商授权**。买法源解决的是"查得到"，解决不了"挂得准"。

---

## 5. 取舍判断

如果只能做三件事：**评测集 + 合规导出（含声明与留痕）+ 本地模型档位**。这三件决定"能不能卖进律所"；全局搜索、协作、质证模板决定"用起来爽不爽"。目前的实现把大量精力放在了模型链路与界面细节上，而这三件门槛事项还停留在待确认清单里——这是当前最大的排期风险。
